Observability for LLM apps

Watching an LLM pipeline
from the inside out

A self-contained POC that ingests source articles into a cross-linked wiki and answers questions grounded in it — with every stage traced, every answer scored for hallucination, and flagged traces recycled into evaluation datasets.

OBJECT LAYER

The wiki app

An ingest pipeline + a grounded chat front end. This is the thing being observed — fixed-function, no magic.

META LAYER

The telemetry

Langfuse (OpenTelemetry-based) records the trace tree, tokens, cost, latency and eval scores of that pipeline.

All instrumentation lives in two files — src/obs.py (traces/scores/sessions) and src/llm.py (the one LLM wrapper). Model, provider and corpus are swappable without touching any tracing code.

What "agents" exist here

Six LLM roles — each one prompt, one model, one traced call

Honest framing: these are fixed-function roles, not autonomous tool-calling agents. There's no dynamic tool selection, MCP, or sub-agents (deliberate POC scope). Each role is hand-wrapped as a Langfuse generation so its model / tokens / cost are captured automatically.

What data is collected

Every span carries far more than a name and a duration

🌳 Structure

Spans for deterministic stages, generations for LLM calls — nested into one tree with parent/child links and timing.

🔢 Tokens & model

Per generation: model, input messages, output, and usage_details — input / output / total tokens. Cost is derived from these.

🏷️ Attributes

gen_ai.data_source.id on RAG spans, http.* url.* on the HTTP child, and a private wiki.* namespace so nothing collides with future OTel keys.

📊 Scores

groundedness · faithfulness · answer_relevance · lint_pass · lint_issue_count — attached to spans as the online-eval signal.

🚦 Status

Failures & low scores set level=WARNING/ERROR with a status_message — the repair loop is visible as a low-score → WARNING → repair sequence.

🔗 Context

Sessions group multi-turn conversations; managed prompts link each generation to a specific prompt version.

Content capture is ON (prompts, tool args, retrieved text, raw results) — reasonable for a self-hosted POC and invaluable for debugging. In production this becomes a redaction policy decision (see the last slide).
How it gets to the backend

Langfuse SDK v4 is OpenTelemetry underneath

Each obs.span()/generation() opens an OTel span in the current context. Because context lives in contextvars, children auto-nest and the trace survives the FastAPI threadpool hop — no manual propagation needed.

What Langfuse gives you back

From raw spans to a debuggable, measurable product

🌳 Traces

The full nested tree per turn/source — click any span to see its exact input, output, and attributes.

💰 Cost · tokens · latency

Per generation and rolled up per trace. Cost comes from model price definitions (added for the custom gateway models).

🎯 Scores over time

faithfulness, groundedness, answer_relevance trended — catch a quality regression as it happens.

🧵 Sessions

Replay a whole multi-turn conversation grouped under one session_id.

📝 Prompt management

Versioned prompts (weak / v1 / v2) linked to the generations that used them — quality changes are attributable.

🧪 Datasets & experiments

Flagged low-faithfulness traces → a golden set → a v1-vs-v2 prompt experiment on that set.

The improvement loop, closed: production traces that hallucinate become the test set that proves the next prompt is better — all inside one tool.

🔍 The debugging story it enables

  • ›A wrong answer is diagnosable end-to-end: retrieval spans log the actual retrieved text, LLM spans log their arguments and raw output.
  • ›A low judge score raises a WARNING, fires the repair loop, and re-judges — the whole self-healing sequence is right there in the tree.
  • ›Every quality change is attributable to a specific prompt version and a specific model.
Future work · the hard part

Context propagation across different agents

This POC is a single fixed pipeline, so context propagation is the easy case. The moment you have multiple agents, tools, or handoffs, keeping one execution as one trace becomes the dominant failure mode — one dropped trace_id fractures the tree into orphans and destroys the whole value proposition.

🤝 Agent → agent handoffs

Nested agents should continue the trace; peer handoffs should use span links + a shared session/conversation id so a multi-agent exchange stays queryable as one unit.

🛠️ Tool & MCP spans

An execute_tool span per tool call, with the downstream DB/HTTP work nesting inside it — reconstructing "the LLM decided X → therefore Y ran." MCP transport is an easy place to drop context.

🔀 Async / queue / webhook boundaries

Every queue, thread, or callback must inject + extract context — the classic @Async context-loss problem. Decide whether a callback continues the trace or starts a linked one; never let it silently orphan.

🧩 Standard gen_ai.* wire attributes

Today model/tokens/cost land in Langfuse's native fields. Auto-instrumentation (OpenLLMetry) emitting standardized gen_ai.* keys would buy portability to a non-Langfuse backend.

Rule of thumb from the checklist: fix propagation before adding any more spans. Verify each boundary with one representative run → it must show as a single trace.
Future work · production hardening

The classical distributed-tracing layer, deferred by design

~80% of LLM observability is tracing you already know. These are POC-optional but must precede any production rollout.

🚏 OTel Collector

Route app → collector → backend instead of exporting direct. The hinge where redaction, batching & routing live.

🕵️ PII redaction

Redact at the collector (redaction processor / Presidio sidecar) before export — centralized and auditable, not in app code.

🎚️ Tail sampling

Keep 100% of error & slow traces, sample a fraction of the successful ones.

🗃️ Retention & storage tiers

Shorter retention for content-bearing spans; large payloads to object storage behind IAM, keep only an app.payload.ref.

📈 Dashboards

The three that pay for themselves: tokens per agent, tokens per model, cost over time.

🔗 Correlation

Tie traces to the existing metrics/logs stack (Grafana / ELK) via shared trace IDs.

Priority order when time is short: 1) context propagation → 2) minimal manual spans → 3) content/redaction policy → 4) version pinning & namespacing → 5) collector, sampling, dashboards.
In one breath

The observability layer is the product
as much as the wiki is.

Two files own all instrumentation. Every stage is a span, every LLM call a traced generation, every answer scored, and every flagged trace a future test case. Swap the model, the provider, or the corpus — the telemetry doesn't change.
